**Helper functions (module-level):**

1. `_free_port() -> int` -- Allocate one free TCP port using socket bind to ("127.0.0.1", 0). Same pattern as `_allocate_tcp_ports` in test_m3_integration.py but for single port.

2. `_allocate_tcp_ports(count: int) -> list[int]` -- Same as test_m3_integration.py pattern, allocate multiple ports at once.

3. `_vcan_available() -> bool` -- Check /sys/class/net/vcan0 exists.

4. `_binary_exists(name: str) -> bool` -- Same as test_m3_integration.py.

5. `_delay_ready(seconds: float) -> Callable[[], bool]` -- Same as test_m3_integration.py.

6. `read_control_state() -> int` -- Same as test_m3_integration.py, reads RTDB system.control_state.

7. `check_control_state(target: int) -> Callable[[], bool]` -- Same as test_m3_integration.py.

8. `wait_for_mqtt_message(host: str, port: int, topic: str, timeout: float = 15.0) -> dict | None` -- Subscribe to MQTT topic on (host, port), wait for first JSON message. Uses paho.mqtt.client with CallbackAPIVersion.VERSION2. Returns parsed dict or None on timeout. Subscribe with QoS 1. Uses loop_start()/loop_stop() pattern.

9. `collect_mqtt_messages(host: str, port: int, topic: str, count: int, timeout: float = 15.0) -> list[dict]` -- Like wait_for_mqtt_message but collects up to `count` messages. Useful for verifying telemetry stream.

Tests:
1. `test_all_modules_alive(m4_system)` -- Check all modules including cloud_manager are alive: `dead = [name for name, m in modules.items() if not m.is_alive]`, assert not dead.

2. `test_cloud_manager_connects(m4_system)` -- Verify cloud_manager connected to MQTT by receiving a heartbeat message on `{prefix}/status`. Use `wait_for_mqtt_message(host, port, "ems/TEST-001/status", timeout=15)`. Assert message is not None. Assert message contains expected keys (e.g., `"state"` or `"online"`).

3. `test_telemetry_reaches_mqtt(m4_system)` -- Subscribe to `ems/TEST-001/telemetry` with `collect_mqtt_messages(host, port, topic, count=2, timeout=30)`. Assert received at least 1 message. Assert message is a dict with data content.

4. `test_cloud_zmq_status(m4_system)` -- Connect a ZMQ SUB socket to the cloud_pub TCP endpoint. Subscribe to "" (all topics). Use RCVTIMEO=10000. Receive one frame, parse msgpack. Verify it contains cloud status data (connected state, broker info). Close socket. This validates CLOUD-08.

5. `test_event_forwarded_to_mqtt(m4_system)` -- Validates CLOUD-03: event forwarding to `{prefix}/events` with QoS 1. Subscribe to `ems/TEST-001/events` with QoS 1 using `wait_for_mqtt_message(host, port, "ems/TEST-001/events", timeout=30)`. The system should generate events naturally during startup (state_change events as control_manager transitions through INIT -> IDLE). If no event arrives within 30s, trigger one explicitly by publishing a mode_change command to `ems/TEST-001/commands` (same as the E2E test pattern) which produces a state_change event that cloud_manager forwards to `{prefix}/events`. Assert message is not None. Assert message is a dict containing event-type keys (e.g., `"type"` or `"event"` with value like `"state_change"`, `"alarm"`, or `"comm_fault"`). This confirms cloud_manager subscribes to ZMQ alarm/event PUB and forwards to MQTT events topic with QoS 1.

**TestE2ERemoteCommand class:**

Class-scoped fixture `m4_system` (same pattern, separate instance).

Tests:
1. `test_e2e_command_flow(m4_system)` -- Full chain per CONTEXT.md E2E table:
   - Step 1: Verify all modules alive.
   - Step 2: Subscribe MQTT test client to `ems/TEST-001/responses/#` BEFORE publishing command (avoid slow-join -- Pitfall 4).
   - Step 3: Generate a unique request_id (uuid4 hex).
   - Step 4: Publish MQTT message to `ems/TEST-001/commands` with JSON: `{"command": "mode_change", "params": {"target_state": "standby"}, "request_id": request_id}`. Use a fresh paho client, connect, publish QoS 1, disconnect.

IMPORTANT: Subscribe to response topic BEFORE publishing command to avoid missing the response (Pitfall 4). Use a separate thread or the collect pattern with background subscription started before publish.
