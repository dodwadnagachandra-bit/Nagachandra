# Requirements: ReVx EMS

**Defined:** 2026-03-14
**Core Value:** Reliable, safe control of battery energy storage — safety manager protects equipment and people, control loop maintains correct power dispatch, system never loses telemetry data.

## v3.0 Requirements

Requirements for M2 — Control & Alarms. Each maps to roadmap phases.

### Control Manager (control_manager)

- [x] **CTRL-01**: 1Hz control loop reads RTDB (BMS, PCS, system sections), evaluates state machine, computes power setpoint, and writes to RTDB system section via seqlock
- [x] **CTRL-02**: State machine implements 8 states (INIT → IDLE → STANDBY → CHARGING → DISCHARGING → FAULT → EMERGENCY → MAINTENANCE) with validated transitions and ZMQ state_change events
- [x] **CTRL-03**: PCS command dispatch writes active power setpoint (0x500E) via comm_manager's Modbus client, with on/off (0x0291) and fault reset (0x5064) sequencing
- [x] **CTRL-04**: Source priority evaluates DAY (Solar > Grid > BESS > DG) and NIGHT (Grid > BESS > DG) modes from control_config.yaml, with MANUAL override via ZMQ command
- [x] **CTRL-05**: SOC-based charge/discharge limits enforce charge_cutoff_pct and discharge_cutoff_pct from config, transitioning to IDLE when SOC limits are hit
- [x] **CTRL-06**: Temperature derating reduces max power when BMS cell temps or PCS temps exceed configurable thresholds, with linear ramp-down curve
- [x] **CTRL-07**: PCS fault handling reads fault words (0x1700-0x1707), transitions to FAULT state, and supports auto-retry (configurable count) or manual reset via ZMQ command
- [x] **CTRL-08**: Power ramping limits setpoint change rate to configurable kW/s to prevent PCS overcurrent and grid disturbance
- [x] **CTRL-09**: Interlock checks verify safety_manager is not in emergency state and PCS is online before allowing STANDBY → CHARGING/DISCHARGING transitions
- [x] **CTRL-10**: ZMQ REQ/REP command API on control_cmd socket accepts mode_change, manual_setpoint, source_priority_override, fault_reset, and maintenance_enter/exit commands
- [x] **CTRL-11**: Hot-reload of control_config.yaml applies new SOC limits, power limits, source priority, and fault_retry_count without restarting the control loop
- [x] **CTRL-12**: Control state and active setpoint published on ZMQ telemetry (topic: control.state, system) at 1Hz for HMI and logger consumption

### Alarm Manager (alarm_manager)

- [x] **ALM-01**: Alarm evaluation reads RTDB signal paths (bms.cell_voltage_max, pcs.internal_temp_c, etc.) at 1Hz and compares against configurable thresholds from alarms_config.yaml
- [x] **ALM-02**: Three-tier IEC 62682 severity (warning, action, protection) with distinct responses: warning = log + DO-2, action = log + power reduction request, protection = log + PCS shutdown request
- [x] **ALM-03**: Alarm lifecycle implements ACTIVE → ACKNOWLEDGED → CLEARED → RETURN-TO-NORMAL state machine per alarm instance, with timestamps at each transition
- [x] **ALM-04**: Hysteresis prevents alarm chattering: alarm activates at threshold, clears at threshold ± hysteresis_pct (configurable per alarm, default 2%)
- [x] **ALM-05**: Delay timer prevents transient spikes from triggering alarms: signal must exceed threshold for delay_ms (configurable per alarm, default 5000ms) before alarm activates
- [x] **ALM-06**: Alarm events published on ZMQ PUSH to logger with alarm_id, signal_path, severity, value, threshold, and lifecycle state
- [x] **ALM-07**: Active alarm list maintained in memory and queryable via ZMQ REQ/REP on alarm_cmd socket (get_active_alarms, acknowledge_alarm, get_alarm_history)
- [x] **ALM-08**: Protection-severity alarms send power reduction or PCS shutdown requests to control_manager via ZMQ REQ on control_cmd socket
- [x] **ALM-09**: Hot-reload of alarms_config.yaml applies new thresholds, hysteresis, delays, and enable/disable flags without restarting the alarm loop
- [x] **ALM-10**: Per-alarm enable/disable flag in config allows site-specific alarm suppression without code changes

## Future Requirements

Deferred to M2.5 or later milestones. Tracked but not in current roadmap.

### Control Manager

- **CTRL-13**: Grid code compliance (CEA India / IEEE 1547 / EN 50549) — frequency droop, voltage ride-through
- **CTRL-14**: Multi-PCS master/slave coordination — pending site engineering decisions (Decision #7.3)
- **CTRL-15**: Reactive power control (power factor, VAr setpoint) — secondary to active power dispatch
- **CTRL-16**: Off-grid mode with frequency/voltage regulation

### Alarm Manager

- **ALM-11**: Alarm shelving (temporary suppression with time-limited auto-restore)
- **ALM-12**: Alarm grouping (suppress child alarms when parent alarm is active)
- **ALM-13**: Alarm analytics (most frequent, longest active, first-out analysis)

### Scheduler (deferred to M3)

- **SCHED-01**: Time-of-day charge/discharge windows from schedule_config.yaml
- **SCHED-02**: 96-point power curve (15-min intervals) for utility dispatch
- **SCHED-03**: Manual/auto mode switching via ZMQ command

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| Scheduler (charge/discharge windows) | Deferred to M3 with HMI — needs UI for curve editing |
| HMI integration | M3 scope — control_manager exposes ZMQ API, HMI consumes it |
| Cloud telemetry forwarding | M4 scope — logger writes local, cloud_manager forwards |
| PCS vendor abstraction layer | Only one PCS vendor (V1.24). Extract when second vendor appears |
| Multi-PCS master/slave | Pending site engineering decisions (Decision #7.3) |
| Grid code compliance | Requires country-specific spec (CEA/IEEE/EN), deferred |
| Alarm shelving/grouping | Advanced IEC 62682 features, deferred to M2.5+ |
| DG auto-start/stop | Requires DG control protocol spec, not available |
