  <action>
    Create stub systemd unit files for all 12 EMS modules and the grouping target. These are deployment scaffolds — actual service logic is deferred to M1+ when modules have real code.

    **1. deploy/systemd/ems.target** — Follow Pattern 8 from RESEARCH.md:
    ```ini
    [Unit]
    Description=EMS — Energy Management System
    Documentation=https://github.com/ReVx-Energy/EMS

    [Install]
    WantedBy=multi-user.target
    ```

    **2. C-based service stubs (safety_manager):**
    Following Pattern 8 from RESEARCH.md exactly:
    - Type=simple
    - ExecStart=/opt/ems/bin/safety_manager
    - Restart=on-failure, RestartSec=5
    - User=ems, Group=ems
    - WorkingDirectory=/opt/ems
    - StandardOutput=journal, StandardError=journal
    - After=network.target, PartOf=ems.target, WantedBy=ems.target

    For safety_manager specifically, add real-time scheduling hints as comments:
    ```ini
    # Real-time priority — requires CAP_SYS_NICE or polkit config
    # LimitRTPRIO=99
    # CPUSchedulingPolicy=fifo
    # CPUSchedulingPriority=80
    ```

    **3. Hybrid module services (comm_manager, data_manager, logger, control_manager):**
    Same structure but ExecStart uses Python via uv:
    - ExecStart=/opt/ems/python/.venv/bin/python -m ems_{module_name}
    - Note in comment: C component launched as subprocess by Python orchestrator

    **4. Python-only services (config_manager, alarm_manager, scheduler, diagnostics, cloud_manager, ota_manager, hmi_server):**
    - ExecStart=/opt/ems/python/.venv/bin/python -m ems_{module_name}
    - Same boilerplate (Type=simple, Restart, User/Group, PartOf)

    For hmi_server, add port binding:
    ```ini
    # HMI serves on port 8080
    Environment=EMS_HMI_PORT=8080
    ```

    **Important consistency rules:**
    - Every service has `PartOf=ems.target` in [Unit]
    - Every service has `WantedBy=ems.target` in [Install]
    - All use User=ems, Group=ems
    - All use WorkingDirectory=/opt/ems
    - All use journal logging (StandardOutput=journal, StandardError=journal)
  </action>

  <name>Task 2: Create dev environment verification script and ECU bring-up checklist</name>
  <files>

  <action>
    **1. tools/verify-dev-env.sh** — Executable bash script that verifies the dev workstation has all required tools and virtual interfaces for EMS development. Used by `make setup` as a post-install verification step.

    The script should:
    - Print a header: "EMS Dev Environment Verification"
    - Check each tool/capability and print PASS/FAIL with clear messages
    - Return exit code 0 if all checks pass, 1 if any fail
    - Track pass/fail count and print summary at end

    Checks to perform:
    1. **cmake** — `cmake --version` succeeds, version >= 3.22
    2. **make** — `make --version` succeeds
    3. **gcc** — `gcc --version` succeeds
    4. **aarch64-linux-gnu-gcc** — cross-compiler available
    5. **uv** — `uv --version` succeeds
    6. **Python 3.12+** — `uv run python --version` reports >= 3.12
    7. **bun** — `bun --version` succeeds
    8. **clang-format** — `clang-format --version` succeeds
    9. **ruff** — `uv run ruff --version` succeeds
    10. **can-utils** — `cansend --help` or `which cansend` succeeds
    11. **socat** — `which socat` succeeds
    12. **vcan kernel module** — `modprobe -n vcan` succeeds (dry-run test, does not require root)
    13. **gpio-sim kernel module** — `modprobe -n gpio-sim` succeeds (dry-run, note: may not be available on all kernels — warn but don't fail)

    Script should be idempotent and safe to run repeatedly. Use `#!/usr/bin/env bash` and `set -euo pipefail` is NOT appropriate here (we want to continue on failures). Instead use manual error tracking.

    Make the script executable: `chmod +x tools/verify-dev-env.sh`

    **2. docs/ecu-bringup-checklist.md** — Document for when the ECU-1170-552A hardware arrives. This captures everything deferred from PLAT-01 that requires physical hardware.

    Sections:
    - **Prerequisites**: Ubuntu 22.04 LTS Advantech BSP ISO, Ethernet cable, USB-serial console cable, micro-SD card
    - **Step 1: Flash BSP**: Instructions for flashing Advantech Ubuntu 22.04 BSP to ECU-1170
    - **Step 2: Network Setup**: Configure static IP on eth0 for SSH access, set hostname to `ems-ecu`
    - **Step 3: Create ems user**: `adduser ems`, add to groups (dialout, can, gpio, sudo)
    - **Step 4: Install EMS dependencies**: apt packages (can-utils, libgpiod-dev, socat, uv, etc.)
    - **Step 5: Verify SocketCAN**: `ip link set can0 type can bitrate 250000`, `ip link set up can0`, `candump can0`
    - **Step 6: Verify RS485**: Check /dev/ttyUSB* or /dev/ttyS* ports, test with `stty` and loopback
    - **Step 7: Verify GPIO (libgpiod)**: `gpiodetect`, `gpioinfo`, test DI/DO with `gpioget`/`gpioset`
    - **Step 8: Deploy EMS**: `make flash` from dev workstation, verify binaries at /opt/ems/bin/
    - **Step 9: Verify Execution**: Run `safety_manager` on ECU, verify ARM64 binary executes
    - **Step 10: Enable systemd services**: `systemctl enable ems.target`, verify startup

    Each step should have a checkbox `- [ ]` for tracking completion and expected output.

    **3. Update Makefile `setup` target** (if not already done in Plan 01) to include a call to `tools/verify-dev-env.sh` at the end of the setup process. If the Makefile from Plan 01 already calls it, skip this. If not, add it as the final step in the setup target.
  </action>
