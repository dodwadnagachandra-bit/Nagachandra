**ZMQ endpoint allocation helper:**

```python
def _allocate_tcp_ports(count: int) -> list[int]:
    """Allocate `count` random free TCP ports for ZMQ endpoints."""
    import socket
    ports: list[int] = []
    sockets: list[socket.socket] = []
    for _ in range(count):
        s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        s.bind(("127.0.0.1", 0))
        ports.append(s.getsockname()[1])
        sockets.append(s)
    for s in sockets:
        s.close()
    return ports
```

Test methods (ordered to follow the 8-step chain from CONTEXT.md):

1. `test_step1_all_modules_healthy(m2_system)`:

2. `test_step2_to_step8_protection_chain(m2_system)`:
   This is the big test. Implements steps 2-8 from CONTEXT.md:

   **Step 2**: Send `mode_change` command to control_manager via ZMQ REQ using `send_control_command(m2_system["control_cmd_endpoint"], ...)` with target=STANDBY. Wait up to 15s for RTDB control_state == STATE_STANDBY via wait_for_criteria.

Write the low-voltage bms_config.yaml to tmpdir, then launch new CAN sim process pointing at it. Wait up to 5s for RTDB min_cell_v < 2.8 via wait_for_criteria (read `rtdb.clusters[0].racks[0].min_cell_v`).

   **Step 4**: Wait up to 7s (5s alarm delay + 2s margin). The alarm_manager should publish a protection-severity alarm. Verify by checking that control_state has transitioned away from STANDBY within 10s total (steps 4+5 combined).

   **Step 5**: wait_for_criteria with check_control_state(STATE_FAULT), timeout=3s. Assert control_state == STATE_FAULT.

   **Step 6**: Verify PCS received shutdown. Connect a pymodbus TCP client to the Modbus simulator (localhost:502). Read register 0x500E (active power setpoint). Assert value is 0 (PCS stopped). Read register 0x0291 (on/off). Assert value is 0 (PCS off). Use `pymodbus.client.ModbusTcpClient`. Timeout: 5s.

   **Step 7**: Kill low-voltage CAN sim, restart with normal voltage config. Wait up to 5s for RTDB min_cell_v > 2.8 via wait_for_criteria.

   **Step 8**: Send `fault_reset` command via ZMQ REQ to control_manager using `send_control_command(m2_system["control_cmd_endpoint"], ...)`. Wait up to 5s for control_state == STATE_IDLE via wait_for_criteria. Use manual fault_reset (not 60s cooldown) per CONTEXT.md decision.

   Key implementation notes:
   - Each step has its own assertion with descriptive message including step number
   - If any step fails, remaining steps are skipped (pytest.fail stops the test)

3. `test_interlock_blocks_dispatch_on_emergency(m2_system)`:
   This test validates CTRL-09: safety emergency state blocks STANDBY -> DISCHARGING transition.

   **Setup**: Ensure control_manager is in STANDBY state first. Send `mode_change` with target=STANDBY via `send_control_command(m2_system["control_cmd_endpoint"], ...)`. Wait for RTDB control_state == STATE_STANDBY.

   **Trigger emergency**: Use the GPIO harness (EMS_GPIO_BACKEND=rtdb) to set DI-2=1 (E-Stop active). This can be done by writing to the RTDB GPIO section directly — attach RTDB, set `rtdb.gpio.di[2] = 1` (E-Stop channel), detach. Wait 2s for safety_manager to process the input and publish emergency state.

   **Attempt blocked transition**: Send `mode_change` command with target=DISCHARGING via `send_control_command(m2_system["control_cmd_endpoint"], ...)`.

   **Assert rejection**: The command response should indicate rejection (check `response["status"] == "error"` or equivalent). Also verify RTDB control_state is NOT STATE_DISCHARGING — it should remain in STATE_EMERGENCY or STATE_STANDBY depending on whether safety_manager already forced the transition.

   **Verify state**: Read RTDB control_state and assert it is STATE_EMERGENCY (safety_manager should have forced this when E-Stop was activated).

   **Cleanup**: Clear E-Stop by setting DI-2=0 in RTDB GPIO section. Wait for safety_manager to process and control_manager to return to a non-emergency state.

   Key implementation notes:
   - EMS_GPIO_BACKEND=rtdb is set in the safety_manager env during fixture setup
   - The GPIO DI mapping: DI-2 = E-Stop (dual-channel, but in simulation mode DI-2 alone suffices)
   - The interlock check happens inside control_manager's state machine transition validation
   - This test proves that the safety -> control interlock works end-to-end in integration

4. `test_control_telemetry_at_1hz(m2_system)`:
   This test validates CTRL-12: control_manager publishes telemetry at 1Hz on its ZMQ PUB socket.

   **Setup**: Create a ZMQ SUB socket and connect to `m2_system["control_pub_endpoint"]` (which is `tcp://127.0.0.1:{control_pub_port}`). Subscribe with topic filter `b"control.state"` (or `b""` for all topics if control_manager uses a `control.state` topic prefix). Set `zmq.RCVTIMEO` to 2000ms to avoid hanging.

   **Collect messages**: Record timestamps of received messages over a 4-second window. Use a loop:
   ```python
   messages: list[float] = []
   deadline: float = time.monotonic() + 4.0
   while time.monotonic() < deadline:
       try:
           msg = sub_sock.recv_multipart()
           messages.append(time.monotonic())
       except zmq.Again:
           break  # recv timeout — no more messages coming
   ```

   **Assert rate**: Assert `len(messages) >= 3` (4 seconds at 1Hz should yield ~4 messages; >= 3 accounts for timing jitter and startup delay). This proves telemetry is flowing at approximately 1Hz.

   **Assert content**: Verify at least one received message can be decoded (msgpack.unpackb) and contains a `"control_state"` field (or equivalent key used by control_manager's telemetry publisher). This proves the messages carry meaningful state data the HMI and cloud modules will consume.

   **Cleanup**: Close the SUB socket in a `finally` block.

   Key implementation notes:
   - The control_pub_port is already allocated in the m2_system fixture — just use the endpoint from the fixture dict
   - ZMQ SUB sockets need a brief sleep (~0.5s) after connect before messages flow (slow joiner problem). Add `time.sleep(0.5)` after connect/subscribe.
   - This test can run after the system has stabilized (modules already running from fixture). No special state transitions required — control_manager publishes telemetry regardless of state.
   - The topic filter depends on how control_manager frames its PUB messages. If it uses multipart `[topic, payload]`, subscribe to the topic bytes. If it uses a single frame with topic prefix, subscribe to the prefix. Check control_manager source for the exact framing. Fall back to empty string subscribe `b""` (all topics) if uncertain, then filter in the test.

   - This validates CTRL-04 (source priority) — specifically the exhaustion path where all sources are unavailable.
