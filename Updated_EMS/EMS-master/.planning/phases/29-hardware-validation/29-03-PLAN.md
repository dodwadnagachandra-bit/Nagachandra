**tools/hw-validation/stage4-gpio-timing.md** — Oscilloscope Measurement Procedure:

Document the manual GPIO timing measurement for safety validation. Include:

1. **Purpose** — Validate safety_manager GPIO response time <100ms p99 on real ECU-1170-552A hardware. Software timestamps are insufficient (miss kernel scheduling jitter, interrupt latency, GPIO driver overhead).

2. **Equipment Required** — Digital oscilloscope (2-channel minimum, >= 1 MSa/s), jumper wires, 3.3V signal source (or jumper wire to toggle DI pins).

3. **Pin Connections** (from gpio_config.yaml):
   - CH1 (trigger): Connect to DI-6 (ESTOP_NO) — GPIO header pin for E-Stop normally-open channel
   - CH2 (measure): Connect to DO-5 (PCS_STOP) — GPIO header pin for PCS emergency stop output
   - Ground: Connect scope ground to ECU GPIO ground pin

4. **Oscilloscope Setup**:
   - Timebase: 50ms/div (covers 0-500ms range)
   - CH1: 1V/div, DC coupling
   - CH2: 1V/div, DC coupling
   - Trigger: CH1 rising edge, level 1.65V (50% of 3.3V)
   - Acquisition: Normal mode, statistics enabled
   - Measurement: CH1-rise to CH2-rise delay

5. **Test Procedure** (step by step):
   - Verify all 14 EMS services are active (`systemctl is-active ems.target`)
   - Verify safety_manager has SCHED_FIFO: `ssh root@ECU journalctl -u safety_manager | grep SCHED`
   - Apply 3.3V to DI-6 (ESTOP_NO) to simulate E-Stop press
   - Observe CH2 (PCS_STOP) assertion on oscilloscope
   - Record propagation delay from CH1 rise to CH2 rise
   - Repeat minimum 100 times for statistical validity
   - Record p50, p95, p99 values

6. **Pass Criteria**: p99 < 100ms

7. **Dual-Channel Cross-Check**: Also measure DI-7 (ESTOP_NC, active-low) — pull LOW to simulate NC channel activating. Both DI-6 HIGH and DI-7 LOW must agree for valid E-Stop. Verify cross-monitoring logic fires DO-5 only when both channels agree.

8. **Failure Investigation**: If p99 > 100ms:
   - Check `uname -r` for `rt` suffix (PREEMPT_RT kernel)
   - Check `chrt -p $(pidof safety_manager)` for SCHED_FIFO priority
   - Check CPU load during test (`top -b -n1`)
   - Check for IRQ storms (`cat /proc/interrupts`)

**tools/hw-validation/soak_monitor.py** — Continuous Soak Test Monitor:
- Shebang: `#!/opt/ems/venv/bin/python3`
- Runs on the ECU for 24 hours (configurable via `--duration` arg, default 86400 seconds).
- Every 60 seconds, checks:
  1. **Service restarts**: `systemctl show {svc} --property=NRestarts` for all 14 services. If any NRestarts > baseline (captured at start), log a RESTART event.
  2. **RSS growth**: For each service, get PID via `systemctl show {svc} --property=MainPID`, read RSS via `psutil.Process(pid).memory_info().rss`. After first 60 samples (1 hour), compute baseline. Flag if current RSS > baseline * 1.10 (10% growth).
  3. **Parquet freshness**: Check most recent .parquet file in `/data/` modified within last 10 seconds. If stale, log DATA_GAP event.
  4. **Disk space**: Check `/data` partition usage. Warn if > 80%.
- Writes each check as a JSONL line to `/data/soak_monitor.jsonl`:
  ```json
  {"timestamp": "...", "check": "heartbeat", "services_ok": 14, "restarts": 0, "max_rss_growth_pct": 2.1, "parquet_fresh": true, "disk_pct": 45}
  ```
- On completion (duration elapsed), writes a summary line:
  ```json
  {"timestamp": "...", "check": "summary", "duration_s": 86400, "total_restarts": 0, "max_rss_growth_pct": 3.2, "data_gaps": 0, "result": "PASS"}
  ```
- PASS criteria: 0 restarts, RSS growth < 10% for all services, 0 data gaps.
- Signal handling: Catches SIGTERM/SIGINT, writes summary before exiting.
- Make executable.

**tools/hw-validation/stage5-soak.sh** — Soak test launcher bash script:
- Accepts ECU_IP as argument.
- **Pre-soak traffic verification (MUST pass before launching 24h monitor):**
  1. **CAN bus check**: Run `ssh root@$ECU_IP "candump can0 -n 1 -T 5000"` (wait up to 5 seconds for one CAN frame). If no frame received within timeout, print "FAIL: No CAN traffic on can0 — ensure CAN simulator is running and connected via USB-CAN adapter" and exit 1.
  2. **Modbus check**: Run `ssh root@$ECU_IP "python3 -c \"from pymodbus.client import ModbusSerialClient; c = ModbusSerialClient('/dev/ttyS1', baudrate=9600, timeout=3); c.connect(); r = c.read_holding_registers(0, 1, slave=1); print('OK' if not r.isError() else 'ERR'); c.close()\""`. If result is not "OK", print "FAIL: No Modbus response on RS485-1 — ensure Modbus simulator is running and connected via USB-RS485 adapter" and exit 1.
  3. Print clear pre-condition documentation at the top of script output:
     ```
     === Stage 5: 24-Hour Soak Test ===
     PRE-CONDITIONS:
       - CAN simulator running on laptop, connected to ECU CAN0 via USB-CAN adapter
       - Modbus simulators running on laptop, connected to ECU RS485 ports via USB-RS485 adapters
       - All 14 EMS services active (run stage1-boot.sh first)
     Checking pre-conditions...
     ```
  4. Only after both CAN and Modbus pre-checks pass, proceed to launch soak_monitor.py.
- SSHs to ECU, copies soak_monitor.py if not present, starts it via nohup so it survives SSH disconnect.
- Prints instructions: "Soak test started. Monitor with: ssh root@ECU tail -f /data/soak_monitor.jsonl"
- Provides a check command: "Check status: ssh root@ECU tail -1 /data/soak_monitor.jsonl"
- Make executable.

**tests/hw/test_soak.py** — pytest wrapper for soak test:
- Module-level: `pytestmark = [pytest.mark.hw, pytest.mark.timeout(90000)]` (25 hours)
- `test_soak_preconditions` — Quick pre-flight check (runs before the 24h test):
  1. Verifies CAN traffic is live: `ecu_ssh("candump can0 -n 1 -T 5000")` returns exit code 0 and non-empty stdout.
  2. Verifies Modbus responds: `ecu_ssh` runs the pymodbus one-liner on the ECU's first RS485 port, asserts "OK" in output.
  3. If either fails, the test fails with a clear message explaining which simulator is missing and how to start it.
  This test is a dependency for `test_soak_24h` — if preconditions fail, the 24h test should not be attempted.
- `test_soak_24h` — Copies soak_monitor.py to ECU via SCP, starts it, waits for completion (polls every 5 minutes by reading last line of soak_monitor.jsonl), then reads the summary line. Asserts result == "PASS".
- This test is EXCLUDED from normal test runs (use `--ignore=tests/hw/test_soak.py` in normal suite). Only run explicitly for the 24-hour soak.
- `test_soak_results_exist` — Quick check: reads /data/soak_monitor.jsonl last line, asserts summary check exists and result is PASS. For use AFTER soak test completes to confirm results in pytest format.

**tools/hw-validation/hw_validation_report.py** — Report generator:
- Shebang: `#!/usr/bin/env python3`
- Reads data from multiple sources to populate the report template:
  1. Stage 1: SSH to ECU and run service checks (or read cached results from `/data/stage1_results.json`)

  3. Stage 3: Read pytest results
  4. Stage 4: Accept manual input via `--gpio-p50`, `--gpio-p95`, `--gpio-p99`, `--gpio-samples` CLI args (oscilloscope data entered manually)
