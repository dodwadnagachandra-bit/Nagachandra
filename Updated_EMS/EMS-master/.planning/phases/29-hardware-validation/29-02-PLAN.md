**tests/hw/test_datapath.py** — Stage 3: Data Pipeline Integrity on ARM64:

Module-level: `pytestmark = [pytest.mark.hw, pytest.mark.timeout(600)]`

Pipeline tests (CAN sim -> RTDB -> ZMQ -> Parquet):
- `test_rtdb_shm_exists` — `ecu_ssh("ls /dev/shm/ems_rtdb*")` returns at least one shm file. This confirms data_manager created the RTDB.
- `test_zmq_telemetry_publishing` — `ecu_ssh("timeout 10 python3 -c \"import zmq; ctx=zmq.Context(); s=ctx.socket(zmq.SUB); s.connect('ipc:///run/ems/telemetry.sock'); s.setsockopt_string(zmq.SUBSCRIBE, ''); msg=s.recv_multipart(); print('OK', len(msg))\"")` — verify ZMQ telemetry socket is publishing. Use the Yocto venv python: `/opt/ems/venv/bin/python3`.
- `test_parquet_files_created` — `ecu_ssh("find /data -name '*.parquet' -newer /tmp/hw_test_marker 2>/dev/null | head -5")` — check Parquet files are being written. First creates a timestamp marker, waits 5 seconds, then checks for newer files.
- `test_parquet_row_count_growing` — SSH to ECU, count Parquet rows at t=0, wait 10 seconds, count again. Assert row count increased. Use pyarrow on the ECU via venv: `/opt/ems/venv/bin/python3 -c "import pyarrow.parquet as pq; ..."`.
- `test_duckdb_query_works` — Run a simple DuckDB query on the ECU against Parquet data: `SELECT COUNT(*) FROM read_parquet('/data/**/*.parquet')`. Verify it returns a result without error.

**tests/hw/test_benchmarks.py** — ARM64 Performance Benchmarks:

Module-level: `pytestmark = [pytest.mark.hw, pytest.mark.timeout(3600)]`

Define benchmark targets as module constants:
```python
CONTROL_JITTER_TARGET_MS: float = 10.0  # +-10ms 1-sigma
RTDB_WRITE_LATENCY_P99_MS: float = 1.0  # <1ms p99
PARQUET_THROUGHPUT_MIN_RPS: float = 1.0  # >=1 row/sec sustained
DUCKDB_QUERY_MAX_S: float = 5.0  # <5s for 24h time_series query
WEBSOCKET_LATENCY_MAX_MS: float = 100.0  # <100ms ZMQ->WS
```

Tests (each runs a measurement script on the ECU via SSH):
- `test_control_loop_jitter` — SSH a Python script to ECU that reads control_manager's tick timestamps from ZMQ telemetry for 60 seconds (shortened from 1 hour for automated test; full 1-hour in standalone benchmark). Calculate tick-to-tick intervals, compute std dev. Assert std dev < CONTROL_JITTER_TARGET_MS. Print actual measured value.
- `test_rtdb_write_latency` — SSH a Python script that does 10,000 RTDB writes via the venv, measures time.monotonic() before/after each write, computes p99. Assert < RTDB_WRITE_LATENCY_P99_MS. Note: this tests RTDB from Python side; C-side latency measured by safety_manager is separate.
- `test_parquet_throughput` — SSH a script that counts Parquet rows at t=0, sleeps 60 seconds, counts again, computes rows/sec. Assert >= PARQUET_THROUGHPUT_MIN_RPS.
- `test_duckdb_query_latency` — SSH a Python script that runs the time_series query pattern from RESEARCH.md (SELECT with 24h window, GROUP BY timestamp). Measures wall clock time. Assert < DUCKDB_QUERY_MAX_S. If insufficient data for 24h query (first boot), use all available data and note in output.
- `test_websocket_latency` — SSH a Python script that connects to the HMI WebSocket endpoint (ws://localhost:8080/ws/telemetry), reads one message, measures the time from ZMQ publish timestamp (embedded in message) to receive time. Assert < WEBSOCKET_LATENCY_MAX_MS. Note: requires hmi_server active.

Each test should:
1. Print the actual measured value (not just pass/fail)
2. Include the target in the assertion message: `assert actual < target, f"RTDB p99 {actual:.2f}ms exceeds {target}ms target"`
3. Use `@pytest.mark.usefixtures("ecu_reachable")` for auto-skip

For SSH-based Python script execution, use a helper pattern:
```python
def run_ecu_python(script: str) -> str:
    """Run a Python script on the ECU via SSH using the Yocto venv."""
    return ecu_ssh(f"/opt/ems/venv/bin/python3 -c '{script}'").stdout.strip()
```
Escape single quotes in scripts by using triple-quoted heredoc-style SSH commands or base64-encoding the script.

  <action>
Create a standalone Python benchmark script designed to run directly ON the ECU (via the Yocto venv) without pytest dependency. This is for use during hands-on hardware bring-up when running pytest from a laptop isn't practical.

**tools/hw-validation/benchmark.py**:
- Shebang: `#!/opt/ems/venv/bin/python3`
- Self-contained — only uses stdlib + packages in Yocto venv (psutil, pyarrow, duckdb, zmq, msgpack).
- Runs all 5 software-measurable benchmarks sequentially:

1. **Control loop jitter** — Subscribe to ZMQ telemetry, extract control_manager tick timestamps for 60s, compute std dev of tick-to-tick intervals.
2. **RTDB write latency** — Import ems_common.rtdb, do 10K writes, measure with time.monotonic(), compute p99.
3. **Parquet write throughput** — Count rows in /data Parquet files at t=0 and t=60s, compute rows/sec.
4. **DuckDB query latency** — Run time_series query over available data, measure wall clock.
5. **WebSocket latency** — Connect to ws://localhost:8080/ws/telemetry, measure end-to-end latency for 10 messages, compute p99.

Output format — structured results to stdout:
```
=== EMS ARM64 Performance Benchmarks ===
Date: 2026-03-16T12:00:00
Host: ECU-1170-552A

[1/5] Control Loop Jitter
  Measured: 3.2ms (1-sigma)
  Target:   10.0ms
  Result:   PASS

[2/5] RTDB Write Latency (p99)
  Measured: 0.45ms
  Target:   1.0ms
  Result:   PASS
...

=== Summary: 5/5 PASS ===
```

Also write results to `/data/benchmark_results.json` with structured data:
```json
{
  "timestamp": "...",
  "hostname": "...",
  "benchmarks": [
    {"name": "control_jitter", "value": 3.2, "unit": "ms", "target": 10.0, "pass": true},
    ...
  ]
}
```

Error handling: If a benchmark fails to run (e.g., service not active), report ERROR (not crash), continue to next benchmark.

Make executable (chmod +x).
