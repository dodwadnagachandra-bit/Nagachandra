**Gathered:** 2026-03-14
**Status:** Ready for planning
**Origin:** Milestone v2.0 audit — cross-phase integration checker found 3 defects

<domain>
## Phase Boundary

Fix 3 C-to-Python ZMQ framing defects. No new features. Minimal, surgical changes to align framing conventions across the C/Python boundary.

</domain>

<decisions>
## Defect Details and Fixes

### DEFECT-1: Double ZMQ PUB Bind on SOCK_TELEMETRY (CRITICAL)

**Problem:** Both `TelemetryPublisher` and `HealthMonitor` in data_manager Python call `bind()` on the same `SOCK_TELEMETRY` endpoint. The second `bind()` fails with "Address already in use."

**Files:**
- `src/data_manager/python/src/ems_data_manager/publisher.py` line 183: `self._pub.bind(self._endpoint)`
- `src/data_manager/python/src/ems_data_manager/health.py` line 53: `self._pub.bind(self._endpoint)`
- `src/data_manager/python/src/ems_data_manager/__main__.py` lines 70-71: both created in same process

**Fix:** HealthMonitor should accept the TelemetryPublisher's PUB socket as a constructor parameter instead of creating and binding its own. One PUB socket, shared within the data_manager process.

**Requirements affected:** DATA-05, DATA-06

### DEFECT-2: PUSH/PULL Framing Mismatch Between C and Python (HIGH)

**Problem:** C PUSH senders (safety_event.c, comm_event.c) send multipart `[4-byte BE length prefix | SNDMORE] [msgpack body]`. Python PULL receiver (event_writer.py) does single-frame `recv()`, gets the 4-byte length prefix as data, `decode_event()` fails. All C-originated events silently lost by logger.

**Files:**
- `src/safety_manager/src/safety_event.c` lines 237-243: multipart send
- `src/comm_manager/c/src/comm_event.c` lines 283-289: multipart send
- `src/logger/python/src/ems_logger/event_writer.py` line 184: single-frame `recv()`
- Python PUSH senders (events.py, manager.py): single-frame send (correct)

**Fix:** Remove the 4-byte length prefix from C PUSH sends. Send a single frame containing just the msgpack body — matching the Python convention. The length prefix was designed for PUB/SUB topic routing but is unnecessary on PUSH/PULL where there's no topic frame.

**Requirements affected:** SAFE-09, COMM-02, COMM-03, COMM-10, LOG-04

### DEFECT-3: PUB/SUB Frame Count Mismatch Between C and Python (HIGH)

**Problem:** C PUB senders send 3 frames `[topic | SNDMORE] [4-byte BE len | SNDMORE] [msgpack body]`. Python PUB senders send 2 frames `[topic | SNDMORE] [msgpack body]`. Logger's telemetry_writer.py drops anything != 2 frames. C-originated PUB messages silently dropped.

**Files:**
- `src/safety_manager/src/safety_event.c` lines 214-225: 3-frame PUB send
- `src/comm_manager/c/src/comm_event.c` lines 264-278: 3-frame PUB send
- `src/data_manager/python/src/ems_data_manager/publisher.py` lines 229-230: 2-frame send
- `src/logger/python/src/ems_logger/telemetry_writer.py` lines 265-268: rejects != 2 frames

**Fix:** Remove the length prefix frame from C PUB sends. Send 2 frames `[topic | SNDMORE] [msgpack body]` — matching the Python convention. The length prefix adds no value on PUB/SUB where ZMQ handles message framing natively.

**Requirements affected:** SAFE-09, COMM-03
